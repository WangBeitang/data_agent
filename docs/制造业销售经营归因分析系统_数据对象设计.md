# 制造业销售经营归因分析系统：数据对象设计

## 0. 文档定位

本文档是 `docs/制造业销售经营归因分析系统_概要设计总纲.md` 的下位设计文档，用于冻结第一版统一分析与经营归因链路中的核心数据对象、字段、枚举、校验规则和对象关系。

本文档重点回答“运行过程中传递什么数据、数据如何约束、对象之间如何关联”。API 请求报文、SSE 事件封装、错误码、逐文件实现位置和开发命令分别由后续 API 设计与模块级实施 SPEC 冻结。

上位约束不变：

- 自然语言问数与经营归因是两项并列一级能力；
- 归因通过多次调用现有问数能力获得事实；
- Planner 只做分析动作选择，不直接提供事实数值；
- 变化额、变化率、贡献率和平均单件销售额由 Python 确定性计算；
- 主要结论必须能够追溯到 Action、SQL、查询结果和 Calculation；
- 第一版所有归因对象均为单次请求内的临时运行时对象，不新增用户、会话、消息、报告、附件等持久化表。

## 1. 当前代码基线与设计边界

### 1.1 现有问数状态继续保留

现有 `app/agent/state.py` 中的 `DataAgentState` 服务于问数 Graph 内部执行，包含关键词、召回字段、召回指标、召回值、表信息、SQL 等状态。

该对象属于既有问数链路内部对象，本期不搬迁、不改名，也不将其直接扩展为归因 State。

新增经营归因使用独立的 `AttributionState`，通过 `QueryService` 调用现有问数 Graph。

### 1.2 QueryService 增加结构化执行结果

现有 `QueryService.search()` 以 SSE 形式直接透传 Graph 自定义事件，可以继续保留用于普通问数兼容。

归因链路需要能够在进程内取得一次问数执行的最终 SQL、结果和状态，因此后续实现应在不破坏现有流式接口的前提下提供结构化 `QueryExecutionResult`。

### 1.3 不重新设计业务库

`dw2` 仍使用现有销售订单星型模型：

- `fact_order`：销售订单事实表；
- `dim_product`：产品/SKU 维度；
- `dim_customer`：终端客户维度；
- `dim_region`：销售区域维度；
- `dim_date`：经营日期维度。

本文件不新增业务表，不修改现有表字段和 115 条业务数据。

## 2. 数据对象设计原则

1. **运行态与持久态分离**：归因对象只存在于单次请求内，不设计 ORM 表。
2. **原始事实与计算结果分离**：SQL 查询结果属于 Observation，Python 派生值属于 Calculation。
3. **原始结果与归一化结果并存**：Observation 保留原始表格，同时提供 Calculator 可稳定消费的统一比较结构。
4. **Planner 输出受控**：Action 使用枚举、白名单维度和受控过滤条件，禁止 Planner 输出 SQL 片段。
5. **引用代替复制**：Evidence 通过 ID 引用 Observation 和 Calculation，不重复存储整份 SQL 与结果集。
6. **状态可判定**：`completed`、`partial`、`failed` 必须由证据和停止规则决定，不能由报告语言决定。
7. **数值口径统一**：`change_rate`、`contribution_rate` 统一保存为小数比例，例如 `-0.2662` 表示 `-26.62%`。
8. **不保存隐藏思考**：Action 的 `reason` 只允许保存简短、可展示的动作目的，不保存模型隐藏推理过程。

## 3. 核心对象关系

```text
用户问题
  │
  ▼
RouteResult
  │ resolved_mode=attribution
  ▼
AttributionTarget
  │
  ▼
AttributionState
  │
  ├── Action[]
  │      │
  │      ▼
  │   QueryService
  │      │
  │      ▼
  ├── Observation[] ───────┐
  │      │                 │
  │      ▼                 │
  ├── Calculation[]        │
  │      │                 │
  │      └────────────┐    │
  │                   ▼    ▼
  ├─────────────── Evidence[]
  │                   │
  ▼                   ▼
Planner             AttributionReport
```

对象职责：

- `RouteResult`：记录最终分析模式；
- `AttributionTarget`：冻结一次归因请求的指标和比较期间；
- `Action`：Planner 给执行环境的受控决策；
- `QueryExecutionResult`：一次问数执行的结构化最终结果；
- `Observation`：将 Action 与实际 SQL/查询结果绑定，并形成归一化环境事实；
- `Calculation`：确定性计算结果；
- `Evidence`：可引用的证据单元；
- `AttributionState`：一次归因请求的完整临时状态；
- `AttributionReport`：面向前端和用户的结构化最终报告。

## 4. 基础枚举

### 4.1 RequestMode

用户请求的分析模式。

| 值 | 含义 |
| --- | --- |
| `auto` | 自动路由 |
| `query` | 强制普通问数 |
| `attribution` | 强制经营归因 |

### 4.2 AnalysisMode

路由后的最终模式。

| 值 | 含义 |
| --- | --- |
| `query` | 普通问数 |
| `attribution` | 经营归因 |

`auto` 只属于请求模式，不能作为最终分析模式。

### 4.3 RouteSource

| 值 | 含义 |
| --- | --- |
| `forced` | 用户通过 `mode` 强制指定 |
| `rule` | 明确关键词规则命中 |
| `llm` | 模糊问题由 LLM 分类 |

### 4.4 AnalysisStatus

| 值 | 含义 |
| --- | --- |
| `running` | 分析执行中 |
| `completed` | 证据充分并完成报告 |
| `partial` | 获得部分证据，但存在明确缺口 |
| `failed` | 无法取得足够有效数据形成归因报告 |

### 4.5 ActionType

第一版严格白名单：

| 值 | 是否查询 Action | 含义 |
| --- | --- | --- |
| `compare_period` | 是 | 比较本期与对比期总体指标 |
| `breakdown_region` | 是 | 按销售区域拆解 |
| `breakdown_category` | 是 | 按产品类别拆解 |
| `breakdown_product` | 是 | 按产品拆解 |
| `breakdown_customer` | 是 | 按客户或客户等级拆解 |
| `analyze_unit_price` | 是 | 取得销售额与销售数量，分析平均单件销售额 |
| `calculate_contribution` | 否 | 对既有拆解 Observation 执行贡献计算 |
| `finish_analysis` | 否 | 结束分析并进入报告生成 |

最多 6 次的限制只统计“查询 Action”。

### 4.6 MetricKey

| 值 | 中文名 | 口径 |
| --- | --- | --- |
| `sales_amount` | 销售额 | `SUM(order_amount)` |
| `sales_quantity` | 销售数量 | `SUM(order_quantity)` |
| `order_count` | 销售订单数 | `COUNT(DISTINCT order_id)` |
| `avg_unit_sales_amount` | 平均单件销售额 | `SUM(order_amount) / SUM(order_quantity)` |

`avg_unit_sales_amount` 不解释为出厂价、含税价、成本或利润率。

### 4.7 DimensionKey

| 值 | 物理来源 | 含义 |
| --- | --- | --- |
| `region` | `dim_region.region_name` | 销售区域 |
| `category` | `dim_product.category` | 产品类别 |
| `product` | `dim_product.product_name` | 产品 |
| `customer` | `dim_customer.customer_name` | 客户 |
| `customer_level` | `dim_customer.member_level` | 客户等级 |

第一版归因 Planner 不允许产生生产、库存、设备、质量、成本、利润、产能等维度。

### 4.8 ObservationStatus

| 值 | 含义 |
| --- | --- |
| `success` | SQL 执行成功且获得可用数据 |
| `empty` | SQL 执行成功但无有效数据行 |
| `failed` | SQL 生成、校验、执行或归一化失败 |

### 4.9 CalculationType

| 值 | 含义 |
| --- | --- |
| `period_change` | 期间变化计算 |
| `contribution` | 维度贡献计算 |
| `unit_price` | 平均单件销售额计算 |

### 4.10 FactorDirection

| 值 | 含义 |
| --- | --- |
| `driver` | 与总体变化方向一致，推动总体变化 |
| `offset` | 与总体变化方向相反，抵消总体变化 |
| `neutral` | 变化为零，或总体变化为零时无法归类为驱动/抵消 |

### 4.11 FilterOperator

第一版只开放：

- `eq`：等于；
- `in`：属于给定集合。

不允许 Planner 直接输出 `where_sql`、SQL 运算符或任意表达式。

## 5. 公共值对象

### 5.1 Period

表示一个闭区间分析期间。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `label` | `str` | 是 | 展示标签，如 `2025年2月` |
| `start_date` | `date` | 是 | 开始日期 |
| `end_date` | `date` | 是 | 结束日期 |

校验：

- `start_date <= end_date`；
- 第一版请求日期必须落在业务数据可支持范围内，否则后续 Observation 可返回空数据或分析进入 `partial/failed`；
- 不在对象层强制两个期间长度完全相同，但固定验收场景均为自然月对比。

### 5.2 FilterCondition

用于受控下钻。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `dimension` | `DimensionKey` | 是 | 过滤维度 |
| `operator` | `FilterOperator` | 是 | `eq` 或 `in` |
| `values` | `list[str]` | 是 | 过滤值，至少 1 个 |

示例：在某一负向产品类别内继续下钻产品时，可使用：

```json
{
  "dimension": "category",
  "operator": "eq",
  "values": ["某产品类别"]
}
```

### 5.3 QueryTable

保存一次问数的原始结果表。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `columns` | `list[str]` | 是 | 原始结果列名 |
| `rows` | `list[dict[str, JsonScalar]]` | 是 | 原始数据行 |
| `row_count` | `int` | 是 | 数据行数 |

`JsonScalar` 只允许：`str | int | float | bool | null`。

`row_count` 必须等于 `len(rows)`。

### 5.4 MetricPeriodValue

同一指标在本期与对比期的数值。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `current_value` | `float | null` | 是 | 本期值 |
| `comparison_value` | `float | null` | 是 | 对比期值 |

### 5.5 ComparisonRow

Calculator 使用的统一归一化行。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `dimension_value` | `str | null` | 是 | 维度成员；总体比较时为 `null` |
| `metric_values` | `dict[MetricKey, MetricPeriodValue]` | 是 | 一个或多个指标的本期/对比期值 |

设计要求：

- `compare_period` 的成功 Observation 正常只有 1 条 `ComparisonRow`，`dimension_value=null`；
- 维度拆解 Observation 每个维度成员对应 1 条 `ComparisonRow`；
- Calculator 只读取 `ComparisonRow`，不直接猜测原始 SQL 列名；
- 原始查询结果仍完整保留在 `QueryTable` 中用于追溯。

## 6. RouteResult

表示意图路由最终结果。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `requested_mode` | `RequestMode` | 是 | 请求传入模式 |
| `resolved_mode` | `AnalysisMode` | 是 | 最终执行模式 |
| `source` | `RouteSource` | 是 | 路由来源 |
| `rule` | `str | null` | 否 | 可展示的简短规则标签，如 `原因类关键词` |

规则：

- `requested_mode=query/attribution` 时，`source=forced`；
- `requested_mode=auto` 时，`resolved_mode` 必须为 `query` 或 `attribution`；
- 不保存 LLM 隐藏推理文本。

---

## 7. AttributionTarget

冻结一次归因分析的业务目标。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `metrics` | `list[MetricKey]` | 是 | 待解释的核心指标，1～3 个 |
| `current_period` | `Period` | 是 | 本期 |
| `comparison_period` | `Period` | 是 | 对比期 |

场景一示例：

```json
{
  "metrics": ["sales_amount"],
  "current_period": {
    "label": "2025年2月",
    "start_date": "2025-02-01",
    "end_date": "2025-02-28"
  },
  "comparison_period": {
    "label": "2025年1月",
    "start_date": "2025-01-01",
    "end_date": "2025-01-31"
  }
}
```

量额背离场景允许：

```json
"metrics": ["sales_quantity", "sales_amount"]
```

平均单件销售额由确定性计算补充，不要求用户问题中显式出现。

## 8. QueryExecutionResult

`QueryExecutionResult` 是 `QueryService` 对“现有问数 Graph 最终执行结果”的统一封装，是普通问数能力与归因 Provider 之间的关键适配对象。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `query` | `str` | 是 | 实际执行的自然语言子问题 |
| `sql` | `str | null` | 是 | 最终通过校验并执行的 SQL；生成前失败时可为 `null` |
| `table` | `QueryTable` | 是 | 原始结果表 |
| `status` | `ObservationStatus` | 是 | `success/empty/failed` |
| `error` | `str | null` | 是 | 失败说明；成功时为 `null` |

约束：

- `success`：`sql != null`、`row_count > 0`、`error=null`；
- `empty`：SQL 执行成功、`row_count=0`；
- `failed`：允许 `sql=null` 或存在已生成 SQL，必须有 `error`；
- SQL 必须是只读查询；
- 该对象不包含 Planner 信息，也不判断归因证据是否充分。

## 9. Action

### 9.1 Action Schema

| 字段 | 类型 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `action_id` | `str` | 是 | - | 单次分析内唯一，如 `a1` |
| `type` | `ActionType` | 是 | - | 动作类型 |
| `metrics` | `list[MetricKey]` | 是 | `[]` | 本动作涉及指标 |
| `current_period` | `Period | null` | 否 | `null` | 本期 |
| `comparison_period` | `Period | null` | 否 | `null` | 对比期 |
| `dimension` | `DimensionKey | null` | 否 | `null` | 拆解维度 |
| `filters` | `list[FilterCondition]` | 否 | `[]` | 受控下钻过滤条件 |
| `source_observation_ids` | `list[str]` | 否 | `[]` | 本地计算动作引用的 Observation |
| `reason` | `str` | 是 | - | 1～200 字的可展示动作目的 |

`reason` 示例：`先比较1月和2月总体销售额，确认下降幅度。`

它是动作说明，不保存逐步思维过程。

### 9.2 Action 条件校验

#### compare_period

- `metrics` 至少 1 个；
- `current_period`、`comparison_period` 必填；
- `dimension=null`；
- 不需要 `source_observation_ids`。

#### breakdown_region

- `dimension=region`；
- 期间必填；
- `metrics` 至少 1 个。

#### breakdown_category

- `dimension=category`；
- 期间必填；
- `metrics` 至少 1 个。

#### breakdown_product

- `dimension=product`；
- 期间必填；
- `metrics` 至少 1 个；
- 允许使用 `category` 等已知过滤条件进行重点下钻。

#### breakdown_customer

- `dimension` 只能为 `customer` 或 `customer_level`；
- 期间必填；
- `metrics` 至少 1 个。

#### analyze_unit_price

- 期间必填；
- `metrics` 至少包含 `sales_amount` 和 `sales_quantity`；
- 平均单件销售额由 Calculator 计算，不允许 LLM 心算。

#### calculate_contribution

- `source_observation_ids` 至少 1 个；
- 只能引用成功的维度拆解 Observation；
- 只能针对 1 个目标指标计算；
- 不计入 6 次查询 Action 上限。

#### finish_analysis

- 不发起查询；
- `reason` 必填；
- 只有停止条件满足或已触发强制停止时才能执行。

### 9.3 Action 去重键

查询 Action 的重复判断使用以下逻辑键：

```text
(type, metrics, current_period, comparison_period, dimension, normalized_filters)
```

`action_id` 和 `reason` 不参与去重。

同一逻辑键不得重复执行。

## 10. Observation

### 10.1 Schema

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `observation_id` | `str` | 是 | 单次分析内唯一，如 `o1` |
| `action_id` | `str` | 是 | 来源 Action |
| `sub_query` | `str` | 是 | Action Router 生成的受控自然语言子问题 |
| `query_result` | `QueryExecutionResult` | 是 | QueryService 原始执行结果 |
| `dimension` | `DimensionKey | null` | 是 | 拆解维度；总体比较为 `null` |
| `normalized_rows` | `list[ComparisonRow]` | 是 | Calculator 可消费的归一化结果 |
| `status` | `ObservationStatus` | 是 | Observation 最终状态 |
| `error` | `str | null` | 是 | 归一化或 Provider 失败说明 |

### 10.2 状态规则

- Provider 失败：`status=failed`；
- Provider 成功但原始结果为空：`status=empty`；
- Provider 成功但无法归一化为预期结构：`status=failed`；
- Provider 成功且归一化完成：`status=success`。

因此 `Observation.status` 是归因环境层的最终状态，可能比内部 `query_result.status` 更严格。

### 10.3 归一化规则

归一化层必须根据 Action 类型和已知指标/维度，将原始结果映射为 `ComparisonRow`，不得把“识别哪个列代表本期/对比期”的任务交给 Calculator 或报告 LLM。

总体销售额对比的 Observation 可以归一化为：

```json
{
  "observation_id": "o1",
  "action_id": "a1",
  "dimension": null,
  "normalized_rows": [
    {
      "dimension_value": null,
      "metric_values": {
        "sales_amount": {
          "current_value": 80009.0,
          "comparison_value": 109030.5
        }
      }
    }
  ],
  "status": "success",
  "error": null
}
```

原始 SQL、原始列名和原始结果仍保存在 `query_result` 中。

## 11. Calculation

Calculation 统一拥有以下公共字段：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `calculation_id` | `str` | 是 | 单次分析内唯一，如 `c1` |
| `type` | `CalculationType` | 是 | 计算类型 |
| `source_observation_ids` | `list[str]` | 是 | 输入 Observation |
| `metric` | `MetricKey` | 是 | 目标指标 |
| `formula` | `str` | 是 | 可展示公式，不是可执行代码 |

### 11.1 PeriodChangeCalculation

额外字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `current_value` | `float` | 本期值 |
| `comparison_value` | `float` | 对比期值 |
| `delta` | `float` | `current_value - comparison_value` |
| `change_rate` | `float | null` | `delta / comparison_value` |

规则：

- `comparison_value=0` 时，`change_rate=null`；
- 不输出 `Infinity`、`NaN` 或人为构造的百分比。

场景一固定结果：

```json
{
  "calculation_id": "c1",
  "type": "period_change",
  "source_observation_ids": ["o1"],
  "metric": "sales_amount",
  "formula": "变化额 = 本期值 - 对比期值；变化率 = 变化额 / 对比期值",
  "current_value": 80009.0,
  "comparison_value": 109030.5,
  "delta": -29021.5,
  "change_rate": -0.2662
}
```

### 11.2 ContributionCalculation

额外字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `dimension` | `DimensionKey` | 拆解维度 |
| `total_delta` | `float` | 总体指标变化额 |
| `items` | `list[ContributionItem]` | 各维度成员贡献 |

`ContributionItem`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `member` | `str` | 维度成员 |
| `current_value` | `float` | 本期值 |
| `comparison_value` | `float` | 对比期值 |
| `delta` | `float` | 成员本期值 - 成员对比期值 |
| `contribution_rate` | `float | null` | `delta / total_delta` |
| `direction` | `FactorDirection` | 驱动、抵消或中性 |

方向规则：

- `total_delta > 0` 且 `item.delta > 0` → `driver`；
- `total_delta > 0` 且 `item.delta < 0` → `offset`；
- `total_delta < 0` 且 `item.delta < 0` → `driver`；
- `total_delta < 0` 且 `item.delta > 0` → `offset`；
- `item.delta=0` → `neutral`；
- `total_delta=0` 时所有 `contribution_rate=null`，不基于贡献率排序为“主要原因”。

由于正负因素可能相互抵消，`contribution_rate` 允许大于 `1` 或小于 `0`。

### 11.3 UnitPriceCalculation

平均单件销售额必须从销售额与销售数量计算。

额外字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `current_sales_amount` | `float` | 本期销售额 |
| `current_sales_quantity` | `float` | 本期销售数量 |
| `current_unit_price` | `float | null` | 本期平均单件销售额 |
| `comparison_sales_amount` | `float` | 对比期销售额 |
| `comparison_sales_quantity` | `float` | 对比期销售数量 |
| `comparison_unit_price` | `float | null` | 对比期平均单件销售额 |
| `delta` | `float | null` | 平均单件销售额变化额 |
| `change_rate` | `float | null` | 平均单件销售额变化率 |

规则：

- 任一期间销售数量为 0 时，该期间 `unit_price=null`；
- 无法计算任一期间平均单件销售额时，`delta`、`change_rate` 根据可用数据置 `null`，禁止补值；
- 固定量额背离场景应得到约 `529.86 → 279.88`。

## 12. Evidence

Evidence 是报告可以引用的最小可追溯证据单元。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `evidence_id` | `str` | 是 | 单次分析内唯一，如 `e1` |
| `action_id` | `str` | 是 | 来源 Action |
| `observation_ids` | `list[str]` | 是 | 来源 Observation |
| `calculation_ids` | `list[str]` | 否 | 相关 Calculation，可为空 |
| `title` | `str` | 是 | 简短证据标题 |
| `statement` | `str` | 是 | 只描述已验证事实的简短陈述 |
| `metric` | `MetricKey` | 是 | 证据对应指标 |
| `dimension` | `DimensionKey | null` | 否 | 对应拆解维度 |
| `member` | `str | null` | 否 | 对应维度成员 |
| `direction` | `FactorDirection | null` | 否 | 驱动/抵消/中性；总体事实可为空 |

规则：

1. `observation_ids` 必须至少包含一个成功 Observation；
2. 证据涉及变化额、变化率、贡献率或平均单件销售额时，必须引用对应 `calculation_ids`；
3. `statement` 不能出现来源对象中不存在的新数值；
4. Evidence 不复制 SQL，前端通过 `observation_ids` 追溯到 SQL；
5. 不设计数值型“置信度”字段。

场景一总体证据示例：

```json
{
  "evidence_id": "e1",
  "action_id": "a1",
  "observation_ids": ["o1"],
  "calculation_ids": ["c1"],
  "title": "2月销售额较1月明显下降",
  "statement": "2025年2月销售额为80009.0，较1月109030.5减少29021.5，降幅约26.62%。",
  "metric": "sales_amount",
  "dimension": null,
  "member": null,
  "direction": null
}
```

## 13. AttributionState

`AttributionState` 是一次归因请求的 LangGraph 临时状态，不持久化。

| 字段 | 类型 | 必填 | 初始值/说明 |
| --- | --- | --- | --- |
| `analysis_id` | `str` | 是 | 单次请求唯一 ID，用于对象关联和日志关联 |
| `question` | `str` | 是 | 原始用户问题 |
| `requested_mode` | `RequestMode` | 是 | 原请求模式 |
| `route` | `RouteResult` | 是 | 路由结果，进入归因时必须为 attribution |
| `target` | `AttributionTarget` | 是 | 指标与比较期间 |
| `actions` | `list[Action]` | 是 | `[]` |
| `observations` | `list[Observation]` | 是 | `[]` |
| `calculations` | `list[Calculation]` | 是 | `[]` |
| `evidences` | `list[Evidence]` | 是 | `[]` |
| `query_action_count` | `int` | 是 | `0`，只统计查询 Action |
| `consecutive_empty_or_failed` | `int` | 是 | `0` |
| `max_query_actions` | `int` | 是 | 第一版固定 `6` |
| `status` | `AnalysisStatus` | 是 | 初始 `running` |
| `report` | `AttributionReport | null` | 是 | 初始 `null` |
| `failure_reason` | `str | null` | 否 | `partial/failed` 时说明主要缺口 |

### 13.1 状态更新规则

- 每生成一个合法 Action，追加到 `actions`；
- 只有查询 Action 实际开始执行时 `query_action_count + 1`；
- 成功 Observation 将 `consecutive_empty_or_failed` 重置为 0；
- `empty/failed` Observation 将其加 1；
- 连续达到 2 时触发停止；
- 达到 `max_query_actions=6` 时禁止继续发起查询 Action；
- 达到上限不自动等于 `completed`；
- 报告生成后才允许填充 `report`。

### 13.2 正常完成判定

进入 `completed` 至少要求：

1. 存在成功的总体指标比较 Evidence；
2. 至少完成两个不同维度的有效拆解；
3. 存在可解释主要变化的驱动因素 Evidence；
4. 当前无新的高价值下钻方向；
5. Planner 选择 `finish_analysis`。

若触发强制停止但只取得部分有效证据，则为 `partial`；若无法形成有效归因报告，则为 `failed`。

## 14. AttributionReport

报告对象严格对应概要设计中的七个报告部分。

### 14.1 Schema

| 字段 | 类型 | 必填 | 对应报告部分 |
| --- | --- | --- | --- |
| `analysis_id` | `str` | 是 | 关联分析 |
| `status` | `AnalysisStatus` | 是 | 报告状态 |
| `question_definition` | `str` | 是 | 1. 问题定义 |
| `core_conclusion` | `str` | 是 | 2. 核心结论 |
| `metric_overview` | `list[MetricOverviewItem]` | 是 | 3. 指标概览 |
| `drivers` | `list[FactorItem]` | 是 | 4. 主要驱动因素 |
| `offsets` | `list[FactorItem]` | 是 | 5. 抵消因素 |
| `evidence_ids` | `list[str]` | 是 | 6. 证据明细 |
| `data_boundaries` | `list[str]` | 是 | 7. 数据边界与建议 |
| `recommendations` | `list[RecommendationItem]` | 是 | 7. 数据边界与建议 |

### 14.2 MetricOverviewItem

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `metric` | `MetricKey` | 指标 |
| `current_period_label` | `str` | 本期标签 |
| `current_value` | `float` | 本期值 |
| `comparison_period_label` | `str` | 对比期标签 |
| `comparison_value` | `float` | 对比期值 |
| `delta` | `float | null` | 变化额 |
| `change_rate` | `float | null` | 变化率，小数比例 |
| `evidence_ids` | `list[str]` | 支撑证据 |

### 14.3 FactorItem

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `title` | `str` | 因素标题 |
| `metric` | `MetricKey` | 目标指标 |
| `dimension` | `DimensionKey` | 拆解维度 |
| `member` | `str` | 维度成员 |
| `delta` | `float | null` | 对总体指标的变化贡献值 |
| `contribution_rate` | `float | null` | 贡献率，小数比例 |
| `summary` | `str` | 基于证据的简短解释 |
| `evidence_ids` | `list[str]` | 支撑证据，至少 1 个 |

`drivers` 中只能放 `direction=driver` 的证据因素，`offsets` 中只能放 `direction=offset` 的证据因素。

### 14.4 RecommendationItem

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `text` | `str` | 建议内容 |
| `evidence_ids` | `list[str]` | 建议依据，至少 1 个 |

建议必须与已确认销售经营因素对应。没有证据时不允许凭常识扩展为生产、成本、库存、供应链等建议。

### 14.5 报告状态约束

- `status=completed`：七部分结构完整，核心原因有 Evidence 支撑；
- `status=partial`：仍输出已有事实和证据，但 `data_boundaries` 必须明确缺口；
- `status=failed`：不生成伪完整归因结论，可只返回失败说明，具体 API 表达由 API 设计冻结。

## 15. Planner 输入边界

Planner 可以读取：

- 原始用户问题；
- `AttributionTarget`；
- 已完成 Action 摘要；
- Observation 的状态和归一化数据；
- Calculation 结果；
- 已形成 Evidence；
- 剩余查询步数。

Planner 不应读取或产生：

- 数据库密码、API Key；
- 任意 SQL 片段；
- 不在白名单中的维度；
- 模型隐藏思考日志；
- 未由 Observation/Calculation 支撑的事实数值。

Planner 每次只输出一个下一步 `Action`。

---

## 16. Action Router 与归一化层约束

Action Router 负责：

1. 校验 Action 枚举和条件必填字段；
2. 校验 Action 是否重复；
3. 校验查询次数上限；
4. 将 Action 转换为受控自然语言子问题；
5. 将维度和过滤条件限制在当前销售经营数据范围内。

Provider/Observation 适配层负责：

1. 调用 QueryService；
2. 保存原始 `QueryExecutionResult`；
3. 按 Action 类型将结果归一化为 `ComparisonRow`；
4. 归一化失败时明确返回 `failed`，不允许 Calculator 猜列。

这两层共同保证 Planner 不直接操纵 SQL，同时保证 Calculator 的输入格式稳定。

---

## 17. 数值精度与展示规则

### 17.1 内部计算

实现时建议使用 Python `Decimal` 或等效方式完成金额和比率运算，再转换为 JSON number 输出；禁止直接让 LLM 完成算术。

### 17.2 输出约定

- 金额、数量、变化额：对象层保存数值，不预先拼接中文单位；
- `change_rate`、`contribution_rate`：保存小数比例；
- 前端展示百分比时自行乘 100 并格式化；
- 对比期为 0：`change_rate=null`；
- 总变化额为 0：`contribution_rate=null`；
- 销售数量为 0：平均单件销售额为 `null`；
- 禁止输出 `NaN`、`Infinity`。

固定验收事实至少应复算得到：

- 2025 年 1 月销售额 `109030.5`；
- 2025 年 2 月销售额 `80009.0`；
- 销售额变化额 `-29021.5`；
- 销售额变化率约 `-0.2662`；
- 2025 年 2 月销售数量 `151`；
- 2025 年 3 月销售数量 `322`；
- 数量变化率约 `1.1325`；
- 2025 年 3 月销售额 `90120.0`；
- 销售额变化率约 `0.1264`；
- 平均单件销售额约 `529.86 → 279.88`。

## 18. 对象生命周期

```text
1. 接收问题
2. 生成 RouteResult
3. 若为 query：进入现有普通问数链路
4. 若为 attribution：解析 AttributionTarget
5. 初始化 AttributionState(status=running)
6. Planner 生成 Action
7. Action Router 校验
8. 查询 Action → QueryService → QueryExecutionResult → Observation
9. Calculator → Calculation
10. Evidence Builder → Evidence
11. 更新 AttributionState
12. Planner 决定继续或 finish_analysis
13. Report Generator 只基于 Evidence 生成 AttributionReport
14. 状态置 completed/partial/failed
15. SSE done 后请求态对象释放
```

第一版页面刷新后允许丢失该状态。

---

## 19. 与普通问数链路的兼容关系

### 19.1 不修改 DataAgentState 的职责

`DataAgentState` 继续承担 SQL 生成 Graph 内部状态；`AttributionState` 不复制其关键词、召回列、召回指标等内部字段。

### 19.2 QueryExecutionResult 是边界对象

归因模块只依赖 `QueryService -> QueryExecutionResult`，不直接依赖问数 Graph 内部节点状态。

这样可以避免归因实现与关键词提取、向量召回、字段过滤等现有内部节点强耦合。

### 19.3 普通问数无需 Evidence

普通 `query` 模式可以直接展示问数结果，不要求为每次普通查询构建 AttributionState、Calculation 或 Evidence。

## 20. 不进入本版的数据对象

第一版明确不设计以下对象：

- User / Role / Permission；
- Tenant；
- Session / Conversation；
- Message；
- PersistentReport；
- Attachment / File；
- AsyncTask / Job；
- Webhook；
- AgentRegistry 或多 Agent 协议对象；
- 生产、设备、质量、库存、成本、利润、产能领域实体。

如后续产品范围扩大，再通过独立设计决策增加，不在第一版提前预留复杂模型。

## 21. 推荐 Python 类型映射

后续实现可按职责采用：

- API 边界、Planner 结构化输出、Report：优先使用 Pydantic Model；
- LangGraph `AttributionState`：使用 `TypedDict` 或与当前项目一致的 LangGraph State 定义；
- 枚举：使用 `str, Enum` 或 Python `StrEnum`；
- 纯计算内部对象：可使用 Pydantic Model 或 dataclass，但对外字段必须与本文档一致。

本文档冻结的是字段语义和校验规则，不强制所有对象必须使用同一种 Python 类型实现。

## 22. 数据对象验收标准

实现完成后至少验证：

1. `RequestMode.auto` 不能成为最终 `AnalysisMode`；
2. 非白名单 Action 被拒绝；
3. 非白名单维度和 SQL 过滤表达式无法进入 Action；
4. 重复查询 Action 可被稳定识别；
5. 查询 Action 总数不超过 6；
6. Observation 同时保留原始 SQL/结果和归一化结果；
7. Calculator 不依赖原始结果列名猜测指标；
8. 对比期为 0 时变化率为 `null`；
9. 总变化额为 0 时贡献率为 `null`；
10. 正负因素同时存在时贡献率允许大于 100% 或为负数；
11. 销售数量为 0 时平均单件销售额为 `null`；
12. Evidence 的数值可追溯到成功 Observation 和 Calculation；
13. Report 的 driver/offset 均有 Evidence 引用；
14. `partial` 报告明确列出证据缺口；
15. 两个冻结演示场景的总体指标可按概要设计固定事实复算；
16. 不新增任何用户、会话、报告、附件等持久化表。

## 23. 冻结结论

第一版归因数据模型冻结为：

```text
RouteResult
+ AttributionTarget
+ Action
+ QueryExecutionResult
+ Observation（原始结果 + 归一化结果）
+ Calculation
+ Evidence
+ AttributionState
+ AttributionReport
```

其中最关键的边界是：

```text
Planner 只产生受控 Action
QueryService 只提供查询事实
Observation 负责事实归一化
Calculator 只做确定性计算
Evidence 绑定事实与计算
Report 只消费 Evidence
```

该模型不扩展项目业务范围，不重构现有问数 Graph，不引入持久化会话或额外基础设施，优先保证第一版两个归因场景和普通问数链路能够稳定跑通、复算和追溯。
