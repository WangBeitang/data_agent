# 制造业销售经营归因分析系统：概要设计总纲

## 0. 文档定位

本文档冻结项目定位、业务边界、总体架构、核心流程、模块职责和验收方向，是后续设计与开发的上位约束。

本文档只回答“做什么、为什么做、总体如何构成”，不展开完整字段、接口报文、逐文件目录和开发命令。后续文档按以下顺序生成：

1. 数据对象设计；
2. API（应用程序接口）设计；
3. 模块级实施 SPEC（实施规格）。

原文件 `docs/项目设计方案.md` 仅作为早期需求来源，不再作为开发依据；与本文档冲突时，以本文档为准。

## 1. 项目身份

### 1.1 项目名称

**制造业销售经营归因分析系统**

### 1.2 业务定位

系统面向制造企业销售经营分析场景，提供两项并列的一级能力：

- **自然语言问数**：将自然语言问题转换为可校验 SQL，查询销售经营数据并返回结构化结果；
- **经营归因分析**：将“为什么”类问题拆成多步分析任务，多次调用问数能力，通过确定性计算形成证据并生成归因报告。

制造业定位限定在**销售经营分析**。当前数据不能支持生产计划、设备、工艺、质量、库存、成本、利润或产能归因。

### 1.3 交付定位

第一版是单用户、单页面、可完整演示的业务原型，重点证明：

- 普通问数链路可独立运行；
- 经营归因链路能够规划并执行多次问数；
- 数值、证据和结论可追溯；
- 两个固定归因场景能够稳定复算。

## 2. 建设目标

1. 保留并产品化现有问数 Graph（工作流图）；
2. 自动区分普通问数与经营归因问题；
3. 通过受控 Planner（规划器）生成多步 Action（分析动作）；
4. 复用问数链路执行每个查询子任务；
5. 使用 Python 计算变化额、变化率、贡献值和平均单件销售额；
6. 将 Action（分析动作）、SQL、结果和计算绑定为 Evidence（证据）；
7. 输出结构化归因报告和贡献图；
8. 在不修改业务表、字段和现有数据的前提下切换制造业销售经营口径。

## 3. 现有基线

### 3.1 问数链路

现有后端已具备并验证以下链路：

```text
用户问题
→ 关键词提取
→ 字段、指标、字段值并行召回
→ 表关系和元数据合并
→ 指标与字段过滤
→ SQL 生成
→ EXPLAIN 校验
→ 必要时修正 SQL
→ 执行 SQL
→ SSE（服务器推送事件）返回结果
```

该链路是项目核心资产，应增量复用，不进行无意义重写。

### 3.2 数据基础

`dw2` 是销售订单星型模型：

| 物理对象 | 本项目业务解释 |
| --- | --- |
| `fact_order` | 销售订单事实表 |

| `dim_customer` | 终端客户维度 |

| `dim_date` | 经营日期维度 |
| `order_quantity` | 销售数量 |
| `order_amount` | 销售额 |
| `member_level` | 客户等级 |

现有数据覆盖 2025 年 1 月 1 日至 2025 年 3 月 31 日，共 115 条销售订单。

产品名、品牌名和类别值视为用于验证分析链路的脱敏合成产品主数据，不描述为某一家真实制造企业的生产数据。

## 4. 范围与非范围

### 4.1 本期范围

#### 自然语言问数

- 查询销售额、销售数量、订单数和平均单件销售额；
- 按时间、区域、产品类别、产品和客户等级统计；
- 展示执行阶段、结果表格和错误信息；
- 保留现有 SQL 生成、校验和修正能力。

#### 经营归因分析

- 识别原因类问题；
- 确定目标指标、本期和对比期；
- 生成并执行受控分析计划；
- 按多个维度拆解并有限下钻；
- 计算变化和维度贡献；
- 区分驱动因素与抵消因素；
- 输出结构化报告和证据明细。

#### 前端展示

- 示例问题和统一输入框；
- 当前分析模式；
- 执行时间线；
- 问数结果表；
- 指标概览、贡献条形图和归因报告；
- SQL 与证据明细；
- 报告复制。

### 4.2 明确不做

- 登录、认证、用户、角色和多租户；
- 会话、消息和报告的服务端持久化；
- 附件上传、文件分析和文件工具；
- 管理员后台、配置热更新和独立日志页面；
- WebSocket（双向长连接）；
- 复杂报告文件管理；
- 生产、设备、质量、库存、成本、利润和产能归因；
- 为包装“多智能体”而拆分无必要 Agent（智能体）。

系统使用默认分析用户；页面刷新后允许丢失当前临时状态。

## 5. 数据与指标边界

### 5.1 业务数据不变

不得修改：

- `dw2` 物理表名和字段名；
- 现有 115 条业务数据；
- 表之间的主外键关系。

允许修改：

- `meta_config.yaml` 中的中文描述、别名和指标口径；
- Prompt（提示词）；
- 页面文案和示例问题；
- 报告口径；
- 新增归因模块的实体名称。

口径修改后允许重建 `meta2`、Qdrant（向量数据库）集合和 Elasticsearch（全文检索引擎）索引。该操作只更新技术元数据，不修改 `dw2` 业务数据。

### 5.2 核心指标

| 指标 | 口径 |
| --- | --- |
| 销售额 | `SUM(order_amount)` |
| 销售数量 | `SUM(order_quantity)` |
| 销售订单数 | `COUNT(DISTINCT order_id)` |
| 平均单件销售额 | `SUM(order_amount) / SUM(order_quantity)` |

原电商化 `GMV` 表达调整为“销售额”。平均单件销售额只表示金额与数量的比值，不扩展解释为出厂价、含税价或利润率。

## 6. 两条一级能力

### 6.1 普通问数

普通问数独立回答“发生了什么”，例如：

- 统计 2025 年各月销售额；
- 查询各销售区域销售额排名；
- 查询各产品类别销售数量；
- 查询 2025 年 2 月各产品销售额；
- 查询黄金等级客户的销售额。

普通问数既是独立产品能力，也是经营归因的数据执行引擎。

### 6.2 经营归因

经营归因回答“为什么发生”，通过多次调用普通问数完成：

```text
总体比较
→ 维度拆解
→ 重点下钻
→ 确定性计算
→ 证据汇总
→ 归因报告
```

经营归因不是只更换 Prompt（提示词），必须增加真实的多步规划、执行、观察和停止机制。

## 7. 冻结演示场景

### 7.1 场景一：销售额下降归因

**问题：为什么 2025 年 2 月销售额较 1 月明显下降？**

固定总体事实：

- 1 月销售额：109030.5；
- 2 月销售额：80009.0；
- 变化额：-29021.5；
- 变化率：约 -26.62%。

推荐路线：

```text
总体销售额比较
→ 区域贡献
→ 产品类别贡献
→ 主要负向类别下钻产品
→ 必要时补充客户等级
→ 汇总驱动和抵消因素
```

### 7.2 场景二：量额背离归因

**问题：为什么 2025 年 3 月销售数量大幅增长，但销售额增长有限？**

固定总体事实：

- 2 月销售数量：151；
- 3 月销售数量：322；
- 数量变化率：约 113.25%；
- 2 月销售额：80009.0；
- 3 月销售额：90120.0；
- 销售额变化率：约 12.64%；
- 平均单件销售额由约 529.86 降至约 279.88。

推荐路线：

```text
销售数量与销售额比较
→ 平均单件销售额变化
→ 产品类别量额结构
→ 重点类别下钻产品
→ 汇总量额背离原因
```

## 8. 总体架构

```text
Vue 3 分析工作台
        │ POST /api/query + SSE
        ▼
AnalysisService（统一分析服务）
        ▼
Intent Router（意图路由器）
   ┌────┴──────────────────┐
   ▼                       ▼
普通问数                 经营归因
QueryService（问数服务）  Attribution Graph（归因工作流）
   │                       ▼
   │                 Planner（规划器）
   │                       ▼
   │                 Action（分析动作）
   │                       ▼
   └──────────────► QueryService（问数服务）
                           ▼
                    现有问数 Graph（工作流图）
                           ▼
                    SQL + 查询结果
                           ▼
                    Observation（观察结果）
                           ▼
                    确定性计算与证据构建
                           ▼
                    结构化归因报告
```

架构原则：

1. 问数和归因是并列能力；
2. 归因通过多次问数获得事实；
3. Planner（规划器）决定分析路线，不提供事实数值；
4. Python 负责确定性计算；
5. LLM（大语言模型）负责意图分类、规划和语言组织；
6. 结论必须追溯到 SQL 和计算证据；
7. 第一版是一个归因 Agent（智能体）调用一个问数子流程，不包装成多个自治 Agent（智能体）。

## 9. 核心模块职责

| 模块 | 职责 | 不负责 |
| --- | --- | --- |
| AnalysisService（统一分析服务） | 统一入口、路由、流式输出 | 生成 SQL、计算贡献 |
| Intent Router（意图路由器） | 区分普通问数和经营归因 | 编写归因结论 |
| QueryService（问数服务） | 调用问数 Graph，返回 SQL、结果和状态 | 选择归因路线 |
| Planner（规划器） | 根据已有证据选择下一步 Action | 直接提供事实数值 |
| Action Router（动作路由器） | 校验 Action 并转换为受控子问题 | 自行改变分析目标 |
| Calculator（确定性计算器） | 计算变化、贡献和比值 | 生成业务解释 |
| Evidence Builder（证据构建器） | 绑定动作、SQL、结果和计算 | 补写缺失事实 |
| Report Generator（报告生成器） | 基于证据生成报告和建议 | 引入无证据原因 |

QueryService（问数服务）及其底层问数 Graph（工作流图）共同承担 Provider（动作执行器与环境结果提供器）职责：执行 Action（分析动作）并返回 Observation（观察结果）。Provider（动作执行器与环境结果提供器）不判断分析是否充分，也不选择下一步。

## 10. 受控 Action（分析动作）

第一版动作白名单：

| Action（分析动作） | 用途 |
| --- | --- |
| `compare_period` | 比较本期和对比期总体指标 |
| `breakdown_region` | 按销售区域拆解 |
| `breakdown_category` | 按产品类别拆解 |
| `breakdown_product` | 按具体产品拆解 |
| `breakdown_customer` | 按客户或客户等级拆解 |
| `analyze_unit_price` | 分析平均单件销售额 |
| `calculate_contribution` | 对已取得结果执行贡献计算 |
| `finish_analysis` | 结束分析并生成报告 |

Planner（规划器）必须输出结构化 Action（分析动作），至少明确动作、指标、本期、对比期、维度和分析理由。完整 Schema（数据结构约束）在数据对象设计中冻结。

## 11. 核心运行流程

### 11.1 意图路由

统一请求支持：

- `auto`：规则优先，模糊问题再由 LLM（大语言模型）分类；
- `query`：强制普通问数；
- `attribution`：强制经营归因。

明显问数表达包括“统计、查询、多少、排名”；明显归因表达包括“为什么、原因、归因、哪些因素导致、增长但、下降原因”。页面展示最终分析模式。

### 11.2 普通问数

```text
路由为 query
→ 调用 QueryService
→ 执行现有问数 Graph
→ 返回执行阶段、SQL 和结果表
```

### 11.3 经营归因

```text
路由为 attribution
→ 初始化 State（规划状态）
→ Planner 选择 Action
→ Action Router 校验并生成子问题
→ QueryService 执行问数
→ Provider 返回 Observation
→ Calculator 执行确定性计算
→ Evidence Builder 形成证据
→ Planner 决定继续或结束
→ Report Generator 生成报告
```

### 11.4 降级

Planner（规划器）输出非法时，携带校验错误重试一次；再次失败则采用通用路线：

```text
总体比较 → 区域拆解 → 类别拆解 → 重点类别下钻 → 汇总
```

该路线只固定顺序，不固定 SQL、结果或答案。

## 12. State、Action、Observation 与 Evidence

- State（规划状态）：一次归因请求的临时上下文，保存问题、期间、指标、动作历史、观察结果、计算、证据、步数、状态和报告；第一版不持久化。
- Action（分析动作）：Planner（规划器）提交给执行环境的结构化决策，必须经过白名单和参数校验。
- Observation（观察结果）：Provider（动作执行器与环境结果提供器）返回的环境事实，包括子问题、SQL、结果、行数、状态和错误。
- Evidence（证据）：将 Observation（观察结果）与确定性计算绑定后的可追溯对象；报告中的主要原因必须引用 Evidence（证据）。

系统不保存或展示模型隐藏思考过程，只展示动作、SQL、结果、公式和结论之间的关系。

## 13. 计算与解释原则

```text
变化额 = 本期值 - 对比期值
变化率 = 变化额 / 对比期值
维度成员贡献值 = 成员本期值 - 成员对比期值
贡献率 = 维度成员贡献值 / 总变化额
平均单件销售额 = 销售额 / 销售数量
```

- 同总体变化方向的成员是驱动因素；
- 反方向成员是抵消因素；
- 因正负因素相互抵消，贡献率允许大于 100% 或为负数；
- 总变化额为零时只展示贡献值；
- 对比期为零时不计算常规变化率；
- 所有关键数值由代码计算，不能让 LLM（大语言模型）心算；
- 当前分析是数据归因，不宣称经过实验验证的因果关系。

## 14. 停止与状态

正常结束至少要求：

1. 完成总体指标比较；
2. 完成至少两个有效维度拆解；
3. 找到能够解释主要变化的驱动因素；
4. 没有新的高价值下钻方向；
5. Planner（规划器）选择结束。

强制约束：

- 最多执行 6 个查询 Action（分析动作）；
- 禁止重复相同 Action（分析动作）；
- 连续两次查询为空或失败时停止；
- 不允许查询不存在的生产、库存、成本等维度。

最终状态：

- `completed`：证据充分并完成报告；
- `partial`：只获得部分证据，报告必须说明缺口；
- `failed`：无法获得足以形成报告的有效数据。

达到步数上限不等于成功。证据不足时不得由 LLM（大语言模型）补写完整原因。

## 15. 归因报告

报告固定为七部分：

1. 问题定义；
2. 核心结论；
3. 指标概览；
4. 主要驱动因素；
5. 抵消因素；
6. 证据明细；
7. 数据边界与建议。

报告不输出未经校准的数值置信度。建议必须与已确认原因对应，不能引入生产、成本、库存等当前数据不支持的解释。

## 16. API 与 SSE 概要

继续使用统一入口：

```http
POST /api/query
```

请求保留 `query`，增加可选 `mode`，默认 `auto`。普通问数和经营归因继续使用 SSE（服务器推送事件），不改为 WebSocket（双向长连接）。

事件类型概要：

| 类型 | 含义 |
| --- | --- |
| `route` | 分析模式已确定 |
| `stage` | 当前执行阶段 |
| `action_start` | 新分析动作开始 |
| `query_result` | 一次问数子任务完成 |
| `calculation` | 确定性计算完成 |
| `report` | 结构化报告完成 |
| `error` | 当前步骤失败 |
| `done` | 整个请求结束 |

完整请求、响应、兼容方式和错误码由 API（应用程序接口）设计定义。

## 17. 前端概要

第一版采用单页工作台：

```text
顶部：项目名称、业务说明、示例问题

左侧：用户问题、分析模式、执行时间线、Action 和 SQL 状态
右侧：问数结果表，或指标概览、贡献图、归因报告和证据
```

最小组件：

- 示例问题；
- 分析时间线；
- 问数结果表；
- 归因报告；
- 贡献条形图。

贡献条形图使用原生 Vue 和 CSS，不增加大型图表依赖。

## 18. 增量改造原则

现有 `app/agent/` 继续承载问数能力，不进行目录搬迁。新增归因能力放入 `app/attribution/`，并增加统一分析服务：

```text
app/
├── agent/                  # 现有问数能力
├── attribution/            # 新增归因能力
├── services/
│   ├── query_service.py
│   └── analysis_service.py
└── api/
    ├── routers/query_router.py
    └── schemas/query_schema.py
```

前端将现有单文件页面拆出时间线、结果表、归因报告和贡献图组件。逐文件职责由模块级实施 SPEC（实施规格）定义。

## 19. 证据、安全与部署边界

### 19.1 证据铁律

1. 报告数值只能来自成功执行的 SQL；
2. 变化和贡献只能由 Python 计算；
3. 主要原因必须关联 Evidence（证据）；
4. 查询不到的数据必须写入数据边界；
5. 不输出伪造置信度；
6. 不把相关性描述成已验证因果关系。

### 19.2 安全边界

第一版不建设完整安全平台，但保留 SQL 校验和修正节点，并限制为只读查询。数据库密码和 LLM（大语言模型）API Key（接口密钥）不得进入文档、日志、SSE（服务器推送事件）或前端响应。

### 19.3 部署边界

- Mac 本地运行前端、后端和进程内 Embedding（向量化）模型；
- 云服务器复用 MySQL、Qdrant（向量数据库）和 Elasticsearch（全文检索引擎）；
- 不增加 Redis、消息队列、调度器或其他常驻服务；
- 本地不使用 Docker（容器）；
- 归因在单次请求内完成，不引入异步任务队列。

## 20. 验收标准

### 20.1 普通问数

固定验证第 6.1 节五个问题，并满足：

- 路由为 `query`；
- SQL 可执行；
- 返回结构化结果；
- 结果与独立 SQL 复算一致；
- 失败时返回明确错误。

### 20.2 经营归因

两个冻结场景均应满足：

- 路由为 `attribution`；
- Action（分析动作）合法且不重复；
- 查询次数不超过 6 次；
- Observation（观察结果）包含 SQL、结果和状态；
- 核心指标与固定事实一致；
- 维度贡献可复算总体变化；
- 主要原因可追溯到 Evidence（证据）；
- 报告区分驱动因素和抵消因素；
- 证据不足时返回 `partial`，不能伪造成功。

不对 LLM（大语言模型）的完整措辞做逐字比较，验收关注结构、数值、证据和状态。

## 21. 建议实施顺序

1. 切换元数据、指标别名、Prompt（提示词）和页面文案；
2. 重建技术元数据并回归普通问数；
3. 让 QueryService（问数服务）提供可复用的结构化 SQL、结果和状态；
4. 增加统一模式与 Intent Router（意图路由器）；
5. 定义 State（规划状态）、Action（分析动作）、Observation（观察结果）和 Evidence（证据）；
6. 实现 Planner（规划器）、Action Router（动作路由器）和停止条件；
7. 实现确定性计算、证据构建和报告生成；
8. 扩展 SSE（服务器推送事件）和前端报告区域；
9. 完成两个归因场景和五个问数问题的端到端验收。

实施期间必须持续保持普通问数基线可用。

## 22. 后续文档约束

- **数据对象设计**：冻结路由结果、State（规划状态）、Action（分析动作）、Observation（观察结果）、Evidence（证据）、计算结果、报告对象、枚举和校验规则；不得增加用户、会话、附件等持久化表。
- **API（应用程序接口）设计**：冻结 `/api/query`、`mode`、SSE（服务器推送事件）、普通问数结果、归因过程、报告、错误码和部分完成语义。
- **模块级实施 SPEC（实施规格）**：最后生成，冻结现有与新增文件映射、依赖方向、实施阶段、验证命令、停止条件和固定验收值。

## 23. 冻结结论

本项目不是将电商页面替换为制造业文案，也不是脱离现有问数能力另建一套归因系统。其核心是：

```text
一级问数执行引擎
+ 受控多步归因编排
+ 确定性计算
+ 可追溯证据
```

第一版成功标准不是功能数量，而是问数与归因两条核心链路均可运行、两个归因场景能够稳定复算、每项关键结论能够追溯到真实 SQL 和计算证据。
